# Audit FinanceApp — 28 Juli 2026

Kondisi: migrasi Supabase → PostgreSQL lokal masih separuh jalan. Build hijau,
tapi banyak fitur keamanan yang **kelihatan jalan padahal tidak**. Itu pola paling
berbahaya di sini: bukan error, tapi diam-diam tidak berfungsi.

Urutan di bawah dari paling kritis. Kerjakan dari atas.

## Konteks deployment — baca ini dulu

Ditemukan setelah audit awal ditulis, dan **mengubah bobot seluruh daftar di bawah**.

Aplikasi ini **sudah live di internet**:

```
financeapp.service (systemd --user, enabled, Restart=always, Linger=yes)
  └─ next start --hostname 127.0.0.1 --port 3000
       WorkingDirectory=/home/frklstn/FinanceApp
nginx → https://cuan.bitkonek.com → 127.0.0.1:3000, TLS via Certbot
```

Konsekuensinya:

1. **Semua P0 di bawah bisa dieksploitasi sekarang**, bukan nanti saat deploy.
   Domainnya publik dan menjawab 200.

2. **Direktori kerja = direktori produksi.** Tidak ada pemisahan dev/prod sama
   sekali. Edit file di sini langsung mengenai yang disajikan ke pengguna;
   `rm -rf .next` menghapus build produksi; `npm run build` menimpanya.
   Pada 28 Juli service tercatat `NRestarts=8` karena hal ini.

3. **Vercel masih aktif di CI dan sekarang berbahaya.** Lihat P0 nomor 0.

Yang sudah benar dan jangan diutak-atik: systemd unit, nginx, Certbot, `Linger=yes`.
Infrastruktur self-host-nya sudah lengkap — tidak ada yang perlu "dipindahkan".

## P0 nomor 0 — Dua produksi yang saling berbeda

`.github/workflows/nextjs.yml` masih berisi:
```yaml
- name: Deploy to Vercel
  run: vercel deploy --prod --yes --token ${{ secrets.VERCEL_TOKEN }}
```

Jadi `git push origin main` **mendeploy ke Vercel**, sementara VPS ini menyajikan
build lokalnya sendiri yang di-`systemctl restart` manual. Dua produksi, dua isi
berbeda, tidak ada yang menyamakan.

Lebih buruk lagi: Vercel tidak punya akses ke PostgreSQL di VPS ini
(`DATABASE_URL` menunjuk localhost). Jadi deployment Vercel-nya kemungkinan besar
rusak/kosong, tapi tetap punya URL yang bisa diakses orang.

**Fix:** hapus step deploy Vercel dari workflow, hapus `vercel.json` dan
`scripts/cleanup-vercel.js`. Sisakan CI-nya untuk lint + build sebagai verifikasi.
Kerjakan **sebelum** push berikutnya.

## P0 — Kritis, bisa dieksploitasi sekarang

### 1. `SESSION_SECRET` punya fallback hardcoded
`src/lib/auth/session.ts:5`
```ts
const SECRET = new TextEncoder().encode(process.env.SESSION_SECRET || 'fallback-dev-secret-change-me');
```
> **Sudah dicek 28 Juli: env var TERPASANG, produksi aman.** Lihat bagian
> "Terverifikasi" di bawah. Yang tersisa adalah bahaya laten, bukan lubang aktif.

Kalau env var tidak terpasang, aplikasi **tetap jalan** memakai string yang ada di
dalam repo ini. Siapa pun yang baca repo bisa menandatangani JWT
`{userId: <siapa saja>}` dan masuk sebagai user mana pun, termasuk superadmin.

Gagalnya diam-diam — tidak ada peringatan sama sekali. Cukup satu kali pindah host
atau satu `.env.local` yang lupa disalin.

**Fix:** lempar error saat startup kalau `SESSION_SECRET` kosong. Jangan kasih default.

### 2. Logout tidak menghapus sesi
`src/components/shared/layout/sidebar.tsx:30`, `mobile-nav.tsx:31`
```ts
// const { error } = await supabase.auth.signOut()
toast('Berhasil keluar!', 'info');
```
Panggilan aslinya dikomentari waktu migrasi, toast sukses dibiarkan. `deleteSession()`
sudah ada di `session.ts:43` tapi **tidak pernah dipanggil dari mana pun**.

User menekan "Keluar", dapat notifikasi berhasil, cookie sesi tetap valid 7 hari.
Di komputer bersama/warnet ini pengambilalihan akun.

**Fix:** server action `logoutAction()` yang memanggil `deleteSession()`, sambungkan
ke sidebar, mobile-nav, dan halaman `/suspended`.

### 3. Google OAuth tanpa parameter `state`
`src/app/api/auth/google/route.ts`

URL otorisasi dibangun tanpa `state`, callback tidak memverifikasi apa pun. Ini
login-CSRF: penyerang bisa memaksa korban login ke akun milik penyerang, lalu
data keuangan yang korban catat masuk ke akun yang penyerang kuasai.

**Fix:** generate `state` acak, simpan di cookie httpOnly, cocokkan di callback.

### 4. Token akses Google tercetak ke log
`src/app/api/auth/google/callback/route.ts:16,31,42`
```ts
console.log('Token response:', tokenData);   // berisi access_token
console.log('User data:', userData);
```
Access token dan data profil masuk ke log server.

**Fix:** hapus ketiga `console.log`.

## P1 — Fitur keamanan yang palsu

### 5. `is_suspended` tidak pernah diperiksa
Admin bisa menekan suspend (`admin.service.ts:42`), kolomnya ter-update, dan
**tidak ada satu baris kode pun yang membacanya**. Middleware hanya cek sesi ada
atau tidak. Halaman `/suspended` tidak pernah tercapai.

Dulu dicek di middleware era Supabase (lihat commit `f2d83bc`), hilang saat migrasi.

**Fix:** cek `is_suspended` di middleware, redirect ke `/suspended`.

### 6. Lupa & reset password pura-pura berhasil
`(auth)/forgot-password/page.tsx:36`, `reset-password/page.tsx:45`
```ts
const error: any = null; // Stubbed Supabase call
```
Karena `error` selalu `null`, UI selalu menampilkan "berhasil". User menunggu email
yang tidak pernah dikirim, dan tidak punya cara memulihkan akun.

Kabar baik: lapisan DB-nya **sudah lengkap** — `setResetToken`, `getUserByResetToken`,
`updatePassword` semua sudah ada di `user.repo.ts`. Tinggal disambung + pengirim email.

**Fix:** server action reset password memakai repo yang sudah ada. Kalau belum ada
layanan email, minimal jangan tampilkan pesan sukses palsu.

### 7. `email_verified` tidak pernah dicek
Kolom ada di tabel `users`, `confirmation_token` juga ada, tidak ada yang membaca.
Login menerima akun yang emailnya belum terverifikasi.

Gabungan dengan OAuth Google (poin 3) ini jadi jalur pengambilalihan: daftar pakai
email orang lain, lalu korban yang login via Google masuk ke akun yang sudah ada.

## P2 — Data & schema

### 8. Halaman Pinjol membaca tabel yang salah
`src/hooks/useDebts.ts` memanggil `getDebtsData()` yang query tabel `debts`
(utang manual), padahal halaman Pinjol butuh `loan_trackers`. Data yang tampil salah.

`debtService.getLoanTrackers()` sudah dibuat, tinggal dipakai.

### 9. Kolom `amount_applied` tidak ada di DB
`DebtForm.tsx:72` menulis field ini, `pinjol/page.tsx:143` membacanya, kolomnya
tidak ada di `sql/init.sql` maupun DB. Akan gagal begitu simpan pinjol diaktifkan.

### 10a. Seluruh repo berubah jadi CRLF — SELESAI didiagnosa, belum ditangani
141 berkas tampak "modified" di `git status`, padahal hanya 58 yang benar-benar
berubah isinya. Sisanya murni pergantian akhir baris LF → CRLF di working tree.

Kalau di-commit apa adanya, perubahan sungguhan akan tenggelam di antara 83 berkas
yang cuma ganti akhir baris.

**Fix:** tambahkan `.gitattributes` berisi `* text=auto eol=lf`, lalu
`git add --renormalize .` sebelum commit pertama.

### 10. `sql/init.sql` belum masuk git
Ini satu-satunya definisi DB lokal yang benar (20 tabel, tanpa RLS). Statusnya
untracked. Kalau hilang, DB tidak bisa dibangun ulang.

### 11. `supabase/` sudah usang tapi masih ter-track
`supabase/schema.sql` + 11 migrasi mendeskripsikan DB yang sudah tidak ada, lengkap
dengan RLS dan `auth.uid()` yang tidak berlaku di Postgres lokal. Dua sumber
kebenaran yang saling bertentangan di satu repo.

**Fix:** hapus, atau pindahkan ke `docs/arsip/` dengan README yang menjelaskan.

### 12a. Tidak ada pemisahan dev/prod
Direktori yang diedit adalah direktori yang disajikan systemd. Tidak ada staging,
tidak ada build terpisah, `npm run dev` dan `next start` berebut folder `.next`
yang sama.

**Fix minimal:** clone kedua untuk kerja (`~/FinanceApp-dev`), VPS hanya menarik
hasil yang sudah jadi. Atau pakai `output: 'standalone'` di `next.config.js` dan
deploy direktori build, bukan direktori sumber.

### 12. Registrasi tanpa validasi
`(auth)/register/actions.ts` — tidak ada validasi format email, tidak ada syarat
kekuatan password, email duplikat jatuh ke `catch` dan keluar sebagai
"Gagal membuat akun" yang membingungkan. `zod` sudah jadi dependency, belum dipakai.

## Sudah beres (28 Juli, sesi kedua)

Terverifikasi langsung di produksi `cuan.bitkonek.com` setelah
`systemctl --user restart financeapp`:

- **P0 nomor 0** — step `Deploy to Vercel` dihapus dari `nextjs.yml` (workflow jadi
  CI verifikasi saja), step trim Vercel dihapus dari `cleanup.yml`, `vercel.json`
  dan `scripts/cleanup-vercel.js` dihapus. Tidak ada lagi produksi kedua.
- **P0 nomor 1** — fallback secret dibuang, diganti `getSecret()` yang melempar
  error kalau env var kosong. Diresolusi saat dipanggil, bukan saat modul dimuat,
  supaya `next build` di CI (tanpa `.env.local`) tetap jalan. Pemanggilannya
  diletakkan di luar `try` pada `verifySession` supaya salah konfigurasi tidak
  tersamar jadi "semua orang belum login".
- **P0 nomor 2** — `logoutAction()` baru di `src/app/actions/auth.ts`, disambungkan
  ke sidebar, mobile-nav, dan halaman `/suspended`. Cookie benar-benar dihapus.
- **P0 nomor 3** — OAuth `state` acak 32 byte, disimpan di cookie httpOnly,
  dicocokkan dengan `timingSafeEqual` lalu dibuang sekali pakai. Diuji:
  `?state=palsu` dan tanpa `state` sama-sama ditolak ke `?error=GoogleStateMismatch`.
- **P0 nomor 4** — tiga `console.log` yang mencetak access token dan data profil
  dihapus; log error tinggal pesannya saja.
- **P1 nomor 5** — suspensi ditegakkan di `workspaceService.getActiveAccountForUser()`
  yang dipakai `requireAccount()`, jadi berlaku untuk semua server action.
  `SuspensionGuard` di layout dashboard hanya untuk pengalihan tampilan.
- **P1 nomor 7 (sebagian)** — callback Google menolak `verified_email === false`.
  Login email/password masih belum memeriksa `email_verified`.
- Bonus: kata sandi placeholder akun OAuth memakai `randomBytes(32)`, bukan
  `Math.random()`.

- **P1 nomor 6 — reset password.** Halaman reset sebelumnya menerima kata sandi
  baru, menampilkan "Password berhasil diperbarui!", lalu mengalihkan ke dashboard
  **tanpa token, tanpa sesi, dan tanpa menyentuh database**. Sekarang:
  - `resetPasswordAction(token, password)` memverifikasi token (sekaligus masa
    berlaku), meng-hash ulang, dan token hangus sekali pakai. Panjang minimum
    divalidasi ulang di server.
  - Halaman reset membaca `?token=` dari URL; tanpa token form tidak ditampilkan
    sama sekali. Setelah berhasil diarahkan ke `/login`, bukan dashboard —
    mengganti kata sandi tidak membuat sesi.
  - Halaman `/forgot-password` berhenti berbohong. Belum ada layanan pengirim
    email, jadi form dicabut dan diganti keterangan jujur.
  - `npm run reset-link -- <email>` untuk admin menerbitkan tautan secara manual.
    Tokennya sengaja tidak dicetak ke log server — itu masalah yang sama dengan
    token Google yang baru dibersihkan.

- **SMTP** — `src/lib/email.ts` (nodemailer, dikonfigurasi lewat env sehingga tidak
  terikat penyedia). `/forgot-password` hidup kembali dan benar-benar mengirim.
  Jawaban untuk email terdaftar dan tidak terdaftar dibuat sama persis supaya
  halaman itu tidak bisa dipakai menebak email siapa yang punya akun. SMTP belum
  dikonfigurasi ditampilkan terang-terangan — itu salah konfigurasi server, beda
  urusan dengan email tidak ditemukan. Diagnosa: `npm run check-smtp`.
- **P2 nomor 10 dan 11** — `sql/init.sql` masuk git (diverifikasi mereproduksi
  persis 20 tabel di database berjalan). `supabase/` dipindah ke `docs/arsip/`
  dengan README yang menjelaskan kenapa tidak boleh dijalankan.
- **Lima skrip mati dihapus** — `apply-remote-migrations`, `create-superadmin`,
  `get-admin-email`, `run-migration`, `seed-categories`. Semuanya butuh
  `@supabase/supabase-js` yang sudah tidak terpasang, dan `run-migration` membaca
  berkas migrasi yang tidak ada. Diganti `npm run superadmin`.
- **`.env.example`** — dokumentasi variabel lingkungan yang dibutuhkan.

Uji: `npm test` — `test:money` 16 assert + `test:auth` 7 assert (token ngawur,
token kedaluwarsa, token sekali pakai, email asing, kata sandi baru berlaku).
Keduanya mengembalikan state DB seperti semula.

## Terverifikasi 28 Juli

**`SESSION_SECRET` terpasang di `.env.local`** (64 karakter acak). `next start`
memuatnya dari `WorkingDirectory`, jadi produksi menandatangani sesi dengan secret
asli — fallback di repo tidak pernah terpakai.

P0 nomor 1 turun bobot: bukan lubang aktif, tapi **tetap harus diperbaiki** karena
gagalnya diam-diam. Kalau suatu saat file `.env.local` hilang atau aplikasi
dipindah ke host lain tanpa env var, aplikasi tetap menyala memakai secret yang
tertulis di repo, tanpa satu pun peringatan. Ganti `||` dengan throw saat startup.

### Rotasi secret — tambahan

Nilai `SESSION_SECRET` sempat tersalin ke transkrip percakapan pada 28 Juli.
Sebaiknya diputar:

```
openssl rand -base64 48          # ganti nilai di .env.local
systemctl --user restart financeapp
```

Efek sampingnya semua sesi yang ada jadi tidak valid, alias semua pengguna
ter-logout paksa. Mengingat tombol logout memang belum berfungsi (P0 nomor 2),
itu justru sekalian membersihkan sesi lama yang menggantung.

## Sisa pekerjaan, berurut

P0 habis. P1 habis kecuali satu bagian yang menunggu keputusan.

1. **Layanan pengirim email** — satu-satunya yang butuh keputusan: Resend, SMTP,
   atau lainnya. Begitu ada, dua hal langsung terbuka: `/forgot-password` bisa
   dihidupkan lagi (alur token-nya sudah jalan penuh, tinggal pengiriman), dan
   verifikasi email bisa dibuat sehingga sisa P1 nomor 7 (login memeriksa
   `email_verified`) bisa ditutup.
2. **P2 nomor 10 dan 11** — commit `sql/init.sql`, arsipkan `supabase/`.
   Cepat, dan menghentikan kebingungan sumber kebenaran schema.
3. **P2 nomor 12a — pisahkan dev/prod.** Kerjakan sebelum P3, karena P3 berarti
   banyak siklus build di direktori yang sedang disajikan ke pengguna.
4. **P2 nomor 8, 9, 12** — pinjol salah tabel, kolom `amount_applied`, validasi
   registrasi pakai `zod` yang sudah jadi dependency.
5. **P3** — halaman satu per satu, pola yang sama seperti Wallets.

### Utang yang sengaja ditinggal

- Mengganti kata sandi **tidak** membatalkan sesi yang sudah terbit. Sesi berupa
  JWT tanpa penyimpanan di server, jadi pembatalan butuh daftar-cabut atau nomor
  versi di profil. Relevan kalau suatu saat ada indikasi akun dibobol.
- Tidak ada pembatasan laju di login, registrasi, maupun penerbitan token reset.

Catatan cara kerja: selama dev/prod belum dipisah, setiap `npm run build` di
direktori ini mengganti yang dilihat pengguna. Kalau mau aman, `systemctl --user
stop financeapp` dulu sebelum bereksperimen, nyalakan lagi setelah build stabil.
